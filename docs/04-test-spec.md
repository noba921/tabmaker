## 1. テストの考え方

### 1.1 何を保証するか

自動採譜は本質的に**正解が一意に定まらない**処理であり、「出力が正しいか」を
一般の楽曲で機械的に判定することはできない。そこで検証の対象を2つに分ける。

| 種別 | 対象 | 判定方法 |
|---|---|---|
| **不変条件** | どんな入力でも必ず成り立つべき性質 | 厳密に判定する |
| **精度** | 統計的にどれくらい当たるか | 正解が既知の合成音源で閾値判定 |

不変条件の例:

- 弦とフレットから元の音高が復元できる
- 同時に鳴る音に同じ弦を割り当てない
- MusicXMLの各小節の音価の合計が拍子と一致する
- MIDIは書き出し→読み込みで一致する

これらが崩れると「譜面として成立しない」ため、精度以前の問題として扱う。

### 1.2 合成音源を使う理由

実際の楽曲では正解の譜面が存在しないため、精度を数値で測れない。
`testsig.py` が**正解が分かっている音源**を生成する。

| 音源 | 内容 | 検証に使う項目 |
|---|---|---|
| `bass.wav` | E2 G2 A2 B2 の4分音符 × 8小節 | 音高の一致率、量子化 |
| `drums.wav` | キック(1,3拍) / スネア(2,4拍) / ハイハット(8分) | 打楽器の検出率 |
| `other.wav` | Eメジャーの三和音 | 和音の運指割り当て |
| `vocals.wav` | 4音のメロディ | 単音化 |
| `chord_harm.wav` + `chord_bass.wav` | I-vi-IV-V(C - Am - F - G) | コード名の一致率 |
| `dyn.wav` | 1拍目のみ強打のキック | ベロシティ推定 |
| `mix.wav` | 上記の合算 | テンポ・小節頭・調 |

**合成音源の限界**: 実際の楽曲にある残響・音の重なり・演奏の揺れが無い。
したがって「ここを通れば実曲でも当たる」とは言えない。あくまで
**退行(デグレード)の検出**が目的である。実曲での品質は手動確認による。

### 1.3 テストの層

| 層 | ファイル | 実行方法 | 所要時間 | 対象 |
|---|---|---|---|---|
| モジュール | `selftest.py` | `selftest.bat` | 約40秒 | 各処理の中身・精度 |
| 結合(API) | `apitest.py` | `apitest.bat` | 約40秒 | HTTP・保存形式・設定 |
| 環境 | `check.py` | `check.bat` | 数秒 | 依存関係・ffmpeg・ポート |
| 手動 | — | 実曲で確認 | — | 実用上の品質 |

いずれも**外部ネットワークを使わない**ため、オフラインで実行できる。

## 2. モジュールテスト仕様(selftest.py)

全57項目。1件でも失敗すると終了コード1を返す。

### T-1 テンポ・拍グリッド(2項目)

| No | 確認内容 | 判定基準 |
|---|---|---|
| 1-1 | テンポが正しく取れている | 推定BPM と 120 の差が3未満 |
| 1-2 | 小節頭が実際の小節線に合っている | 推定した1小節目の頭が、真の小節線から0.12秒以内 |

> 1-2 は過去に実際に失敗した項目。オンセット強度がスネアに引っ張られ、
> 全小節が1拍ずれていた(詳細設計書 §2.2)。

### T-2 ベース採譜(3項目)

| No | 確認内容 | 判定基準 |
|---|---|---|
| 2-1 | 音符の数がだいたい合っている | 検出数と正解32音の差が4以内 |
| 2-2 | 音高が8割以上一致 | 各拍の±0.5拍以内に正しい音高が存在する割合 > 80% |
| 2-3 | 16分グリッドに量子化されている | すべての開始拍が 1/4 の倍数 |

### T-3 TAB譜への変換(6項目) — **不変条件**

| No | 確認内容 | 判定基準 |
|---|---|---|
| 3-1 | 弦とフレットから元の音高が再現できる | `開放弦 + フレット == 音高` が全音符で成立 |
| 3-2 | フレット番号が範囲内 | 0 ≤ fret ≤ 20 |
| 3-3 | ポジション移動が抑えられている | 使用フレットの幅が7以内 |
| 3-4 | ギターも弦/フレットが正しい | 和音を含む場合でも 3-1 が成立 |
| 3-5 | 同時に同じ弦を使っていない | 同一拍の弦番号に重複がない |
| 3-6 | カポ/変則チューニングでも整合 | ドロップD + カポ2 で `開放弦 + カポ + フレット == 音高` |

### T-4 ドラム採譜(3項目)

| No | 確認内容 | 判定基準 |
|---|---|---|
| 4-1 | キックの検出率 | 正しい拍にキックが検出された割合 > 70% |
| 4-2 | スネアの検出率 | 同上 > 70% |
| 4-3 | ハイハットが検出できている | 検出数 > 小節数 × 拍数 |

### T-5 MusicXML / MIDI の書き出し(17項目)

| No | 確認内容 | 判定基準 |
|---|---|---|
| 5-1 | MusicXMLがパースできる | ルート要素が `score-partwise` |
| 5-2 | パート数が一致 | 4パート |
| 5-3〜10 | 各パートの小節数と音価 | **全小節の音価合計が `拍数×4` と一致**(パートごとに2項目) |
| 5-11 | TABに弦/フレットが全音符分ある | `<technical>` の数 == 音符数 |
| 5-12 | TABクレフが出ている | `<clef><sign>TAB` |
| 5-13 | 打楽器クレフが出ている | `<clef><sign>percussion` |
| 5-14 | ドラムがunpitchedで書かれている | `<unpitched>` が存在 |
| 5-15 | MIDIヘッダが正しい | 先頭4バイトが `MThd` |
| 5-16 | MIDIトラック数 | テンポ用1 + パート2 = 3 |
| 5-17 | テキストTABに小節線がある | `|` の数 > 小節数 |

> 5-3〜10 が最も重要。音価の合計が拍子と食い違うと MuseScore が読み込みに失敗する。

### T-6 コード進行の認識(3項目)

| No | 確認内容 | 判定基準 |
|---|---|---|
| 6-1 | コード区間が取れている | 4区間以上 |
| 6-2 | コード名が3/4以上一致 | C - Am - F - G の一致率 ≥ 75% |
| 6-3 | コード区間の拍位置が妥当 | 開始拍 ≥ 0 かつ 長さ > 0 |

### T-7 MIDIの読み書き(5項目) — **不変条件**

書き出したMIDIを自前のリーダーで読み戻し、元のデータと突き合わせる。

| No | 確認内容 |
|---|---|
| 7-1 | 音符数が一致 |
| 7-2 | 音高が往復しても一致 |
| 7-3 | ベロシティが往復しても一致 |
| 7-4 | 発音時刻が往復しても一致(誤差0.01秒未満) |
| 7-5 | 音の長さが往復しても一致(誤差0.02秒未満) |

### T-8 ドラムのベロシティ推定(2項目)

| No | 確認内容 | 判定基準 |
|---|---|---|
| 8-1 | 強く叩いた打点のベロシティが高い | 1拍目の平均 > その他の平均 + 10 |
| 8-2 | ベロシティが一定値になっていない | 値の種類が2以上 |

### T-9 MusicXMLのコードネーム(4項目)

| No | 確認内容 |
|---|---|
| 9-1 | `<harmony>` が指定した数だけ書かれている |
| 9-2 | コードのルートが正しい |
| 9-3 | マイナーとして書かれている |
| 9-4 | **コードを入れても各小節の音価合計が崩れない** |

### T-10 エンジンの切り替え(12項目)

| No | 確認内容 |
|---|---|
| 10-1 | 5つの処理段が登録されている |
| 10-2〜6 | 各処理段で、使えるエンジンが選ばれている(未導入時はGPU前提に落ちない) |
| 10-7 | 設定が保存される |
| 10-8 | 設定した値が使われる |
| 10-9 | 壊れた設定でも既知のエンジンに落ちる |
| 10-10 | CUDAの検出が例外を出さない |
| 10-11 | デバイス指定が効く |

## 4. 環境診断(check.py)

自動判定ではなく、問題の**原因を人が読める形で示す**ことが目的。

| 項目 | 内容 |
|---|---|
| [1] | Pythonのバージョン(3.10〜3.12を推奨) |
| [2] | 必須ライブラリと、オプションエンジンの**実際のimport結果** |
| [2a] | numpy と scipy の相性、および修復コマンドの提示 |
| [2b] | 各処理段で実際に使われるエンジン |
| [3] | ffmpegの探索結果 |
| [4] | ポート8766の空き |
| [5] | フォルダのパス長(80文字制限) |
| [6] | `server.log` の末尾15行 |

> [2] で `find_spec` ではなく実際の import を行うのは、
> 「インストール済みだが読み込めない」状態を検出するため(詳細設計書 §8.2)。

## 5. 手動確認項目

自動化できない、または合成音源では確認できない項目。

| No | 確認内容 | 合格条件 |
|---|---|---|
| M-1 | 実際の楽曲で最後まで処理が完走する | エラーなく譜面が表示される |
| M-2 | MusicXMLがMuseScoreで開ける | 警告なく読み込め、TAB譜として表示される |
| M-3 | MIDIがDAWで再生できる | パートが分かれ、ドラムが正しい音で鳴る |
| M-4 | 再生位置が譜面と合っている | 曲の後半でもずれない(テンポ変動への追随) |
| M-5 | 検索から採譜まで操作が繋がる | 検索 → 採譜 → 譜面表示が滞りなく進む |
| M-6 | 小節頭の補正が意図通り効く | ボタン1回で1拍ずれる |
| M-7 | 処理時間が要件内 | 4分の曲で15分以内(N-01) |
| M-8 | 容量が要件内 | 4分の曲で15MB以内(N-05) |
| M-9 | エンジンを切り替えると結果が変わる | 設定変更後の曲に反映される |
| M-10 | ブラウザでOpusが再生できる | Chrome / Edge / Firefox |

## 7. 退行が起きやすい箇所

| 箇所 | 起きた/起こりうる問題 | 守っているテスト |
|---|---|---|
| 小節頭の推定 | 全小節が1拍ずれる | T-1-2 |
| ドラムの帯域判定 | 帯域幅の違いで特定の打楽器が0%になる | T-4-1, T-4-2 |
| MusicXMLの休符充填 | 音価の合計が合わずMuseScoreが読めない | T-5-3〜10, A-7-4 |

| 依存の版 | numpy/scipy のABI不整合で全体が動かない | check.py [2a] |
