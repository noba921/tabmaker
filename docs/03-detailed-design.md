## 1. 時間軸の設計 — なぜ秒ではなく拍で持つか

譜面は「何秒に鳴ったか」ではなく「何拍目に鳴ったか」で決まる。
そこで内部表現をすべて拍に統一し、秒との変換を1か所(`analysis.Grid`)に閉じ込めた。

### 1.1 Grid クラス

保持するもの:

| 属性 | 内容 |
|---|---|
| `beat_times` | 拍の**時刻の配列**(等間隔とは限らない) |
| `tempo` | 平均BPM(表示とMIDI出力用) |
| `beats_per_bar` | 1小節の拍数 |
| `phase` | 最初の小節頭が `beat_times` の何番目か |

変換は配列の添字に対する線形補間で行う。

```
時刻 t → 拍:  np.interp(t, beat_times, [0,1,2,…]) - phase
拍 b → 時刻:  np.interp(b + phase, [0,1,2,…], beat_times)
```

**なぜ一定テンポで計算しないか**: 生演奏はテンポが揺れる。平均BPMだけで換算すると、
曲の後半で譜面と音源が数拍ずれる。拍の時刻を配列で持てば、揺れをそのまま吸収できる。

配列の範囲外(イントロ前・アウトロ後)は平均テンポで外挿する。

### 1.2 量子化

演奏の揺れを含む発音時刻を、16分音符(1/4拍)の格子に丸める。

```
量子化後の拍 = round(拍 × 4) / 4
```

**16分にした理由**: 32分まで刻むと、演奏の揺れやピッチ推定の遅れがそのまま
細かい音符として現れ、譜面が読めなくなる。8分では速いフレーズが潰れる。
ポップス・ロックの採譜では16分が実用的な分解能。

音の長さは最低 0.25拍(16分音符)を保証する。長さ0の音符は譜面に書けないため。

## 2. 小節頭の推定

### 2.1 Beat This! を使う場合(既定)

モデルが拍とダウンビートの両方を出力するので、ダウンビートを拍列の添字に対応づける。

```
1. 各ダウンビート時刻に最も近い拍の添字を求める
2. その拍との時刻差が半拍未満のものだけ採用する(誤対応の除去)
3. phase = 最初の添字
4. beats_per_bar = 添字の差分の中央値(2〜12に制限)
```

差分の中央値を使うことで、拍子が3/4や6/8の曲にも自動で対応できる。

### 2.2 librosa を使う場合(フォールバック)

`librosa.beat.beat_track` は拍しか返さないので、小節頭を自前で推定する。

**着眼点**: ポップス・ロックでは小節の1拍目にバスドラムが来ることが多い。
そこで「低域の打点が強い拍」を小節頭とみなす。

```
1. 全体のオンセット強度 strength を求める
2. 200Hz以下に絞ったメルスペクトログラムからオンセット強度 low_env を求める
3. score = 0.25 × 正規化(strength) + 正規化(low_env)
4. 位相 p ∈ {0,1,2,3} ごとに score[p::4] の平均を取り、最大の p を採用
5. 僅差(5%以内)なら小さい p を優先する
```

**設計上の失敗と修正**: 当初は「全帯域のオンセット強度」を主に使っていたが、
スネアは広帯域で音量も大きいため、オンセット強度は**2拍目・4拍目で最大**になる。
その結果、8小節すべてが1拍ずれるという症状が出た。

対策として (a) 低域のオンセット強度を主たる手がかりに変え(重み1.0)、
(b) 全帯域の重みを0.25まで下げ、(c) 僅差では曲頭を優先する、の3点を入れた。

さらに、この推定は**原理的に外れうる**(ドラムなしのイントロ、裏拍にキックが来る曲)ため、
UIに「小節の頭を1拍ずらす」ボタンを用意し、人が直せる逃げ道を残している。

### 2.3 テンポの取り直し

`beat_track` が返すテンポは倍テンポ・半テンポにずれることがある。
検出した拍の間隔の中央値から `60 / 中央値` として計算し直す。

## 3. 音符の推定

### 3.1 ステム単位のキャッシュ

ギターとピアノは、6ステム分離でない場合どちらも `other` を使う。
そのまま実装すると同じ音声に対して推論が2回走る。

そこで**ステムのパスをキーにした推論結果のキャッシュ**を持ち、
パートごとの音域(`lo`〜`hi`)で後からフィルタする。
キャッシュ用のパラメータは、同じステムを使うパートの設定を統合したもの
(音域は和集合、閾値は最も緩い値)を使う。

これで `other` に対する推論が1回で済み、採譜時間がほぼ半減する。

### 3.2 単音化(ベース・メロディ)

ベースとボーカルは単音として扱う。推論結果の重なりを次の規則で解消する。

```
音を開始時刻順に見て、直前の音と重なっている場合:
  - 開始時刻の差が0.06秒未満 → ほぼ同時。片方を捨てる
      ベース  : 低い方を残す(ルート音を優先)
      メロディ: 振幅が大きい方を残す(主旋律を優先)
  - それ以上離れている → 直前の音を切って、この音を鳴らす
残った音のうち長さ0.05秒未満のものは捨てる
```

**残す基準を楽器で変える理由**: ベースは倍音が強く出るため、実際より高い音が
同時に検出されやすい。低い方を残すのが正しい。ボーカルは逆に、装飾的な音より
主旋律の方が振幅が大きいので、振幅で決める方が良い。

### 3.3 和音の制限(ギター・ピアノ)

50ms以内に始まる音をひとつのまとまりとみなし、振幅の大きい順に**最大6音**まで残す。
ギターの弦は6本しかなく、それを超える和音は運指を割り当てられないため。

## 4. ドラムの採譜

### 4.1 帯域の正規化 — 設計上の要点

内蔵の判定では、打点ごとに帯域のパワーを比べて種類を決める。ここに落とし穴がある。

**問題**: 単純に帯域ごとのパワーの**合計**を比べると、周波数ビンの数が多い高域が常に勝つ。

| 帯域 | 周波数 | FFTビン数(n_fft=2048, 44.1kHz) |
|---|---|---|
| low | 20〜130Hz | 6 |
| body | 130〜400Hz | 12 |
| noise | 1500〜8000Hz | 302 |
| high | 8000〜17000Hz | 418 |

低域は6ビンしかないため、バスドラムがどれだけ強く鳴っていても合計では勝てず、
**キックの検出率が0%になった**。

**逆の失敗**: ビン数で割って平均を取ると、今度は狭い帯域に集中する音が有利になりすぎる。
190Hzの胴鳴りを持つスネアが「タム」と判定されるようになった。

**採用した方法**: 帯域ごとに、**その曲の中でのその帯域の最大値(99.5パーセンタイル)**で
正規化する。帯域どうしを直接比べるのをやめ、「この帯域にとって大きい音か」を見る。
帯域幅の違いが影響しなくなり、曲ごとのミックスの差にも強い。

```
env[帯域] = clip(帯域のパワー平均 / percentile(帯域のパワー平均, 99.5), 0, 1.5)
```

### 4.2 判定規則

```
n = 打点前後55msにおける各帯域の env の最大値

n[low]   > 0.30                        → キック
n[noise] > 0.30                        → スネア
  そうでなく n[body] > 0.35 かつ n[low] < 0.30 → タム
n[high]  > 0.28 かつ n[high] > 0.55×n[noise] → シンバル系
    減衰 > 0.55 → クラッシュ
    減衰 > 0.38 → オープンハイハット
    それ以外    → クローズドハイハット
どれにも該当しなければ、最大の帯域から決める
```

1つの打点に複数の打楽器を割り当てられる(キックとハイハットの同時打ちなど)。

**減衰の測り方**: 打点から0.12〜0.28秒後の高域の残り具合を見る。
ただし**次の打点の0.02秒前まで**に制限する。これをやらないと、次のハイハットの音を
「減衰していない」と誤読し、すべてクラッシュと判定してしまう。

### 4.3 ベロシティの推定

ADTOF等の採譜モデルは音符の位置は当てられるが、強弱を返さない。
分離ステムのラウドネス曲線から推定する(arXiv:2509.24853 の後処理と同じ考え方)。

```
1. スペクトログラムにA特性重み付けを掛ける(聴感に近づける)
2. 打楽器ごとに対応する帯域の env を取る
3. 打点位置の値を dB に変換する
4. 打楽器の種類ごとに、10〜95パーセンタイルで正規化する
5. ベロシティ = clip(45 + 82 × 正規化値, 35, 127)
```

**種類ごとに正規化する理由**: キックとハイハットでは絶対的な音量が違う。
全体で正規化するとハイハットが常に弱く見える。
「そのハイハットの中で強いか」を見るのが音楽的に正しい。

## 5. コード進行の推定

### 5.1 外部ライブラリを使わなかった理由

候補として autochord / BTC / ChordMini を検討したが、

- autochord は TensorFlow と NNLS-Chroma の VAMP プラグインが必要で、Windowsで詰まりやすい
- BTC / ChordMini は学習済み重みの入手と配置が手作業になる

一方でコード認識は、テンプレート照合 + 平滑化 + ベース音による補正という
古典的な構成でも実用的な精度が出る。**追加ダウンロードが不要**という利点が大きいため、
自前実装を選んだ。差し替えられるようエンジンとして分離してある。

### 5.2 アルゴリズム

```
1. ドラム以外のステムを足して和声成分だけの音を作る
2. CQTクロマ(12次元)を求める
3. 拍の境界でフレームを区切り、拍ごとの中央値を取る
   → コードは拍の頭で変わることが多く、拍内の平均化はノイズを減らす
4. 49種のテンプレートとのコサイン類似度を求める
      12種 × {maj, min, 7, min7} + N.C.
5. ベース音のクロマでルートを補正する(+0.18 × ベースのそのルート音の強さ)
6. 音が薄い拍(下位12%)は N.C. に寄せる
7. ビタビ探索で平滑化する(自己遷移確率0.90)
8. 同じコードが続く区間をまとめる
```

### 5.3 パラメータの根拠

| パラメータ | 値 | 理由 |
|---|---|---|
| テンプレートの重み | ルート1.0 / 3度0.9 / 5度0.8 | 5度は他のコードとも共有されるため識別力が低い |
| 7thコードの補正 | −0.05 | 構成音が多い分だけ類似度が上がりやすく、放置すると7thを出しすぎる |
| ベース補正 | +0.18 | 転回形や分数コードでの誤りを減らす。強くしすぎるとベースの経過音に引きずられる |
| 自己遷移確率 | 0.90 | 低いとコードが1拍ごとに揺れる。高すぎると転調やサビの変化に追随しない |
| softmax温度 | 0.08 | 類似度の差を確率の差に変換する鋭さ |

### 5.4 出力

拍単位の区間として持ち、1拍未満の孤立したコードは前の区間に吸収する。
MusicXMLへは `<harmony>` として、先頭パートの小節内の正しい位置に挿入する。

## 6. 運指の最適化

### 6.1 問題設定

同じ音高でも、ギターでは複数の弦・フレットの組み合わせで出せる。
たとえば E4(MIDI 64)は 1弦0f / 2弦5f / 3弦9f / 4弦14f のいずれでも出せる。

**目的**: 音高の列が与えられたとき、**左手の移動が少なく、押さえやすい**
弦・フレットの割り当てを選ぶ。

これは各音符が状態を持つ系列上の最適化問題であり、**動的計画法**で解ける。

### 6.2 手順

```
① 音域外の音をオクターブ単位で移動して収める
② 同時発音でグループ化する
③ グループごとに、可能な弦・フレットの割り当てを列挙する
     - 高い音ほど細い弦(弦の添字が小さい)という制約を課す
     - フレットは 0 〜 max_fret
     - 2音以上でフレットの開き(スパン)が5を超えるものは除外
④ 割り当てごとに「押さえにくさ」を計算し、上位6件に絞る
⑤ グループ間を動的計画法でつなぐ
⑥ 最小コストの経路を復元する
```

### 6.3 コスト関数

**押さえにくさ(グループ内)**

```
コスト = 0.9 × スパン
       + 0.03 × 押さえるフレットの平均      ← 低い方が弾きやすい
       + 0.15 × 弦の飛び越し数              ← 弦をまたぐと弾きにくい
       − 0.35 × 開放弦の数                  ← 開放弦は楽
```

**移動コスト(グループ間)**

```
コスト = 0.45 × |今のポジション − 前のポジション|
```

ポジションは「押さえているフレットの最小値(開放弦を除く)」とする。
全部開放弦のグループはポジションを持たないので、前のポジションを引き継ぐ。

### 6.4 係数の決め方と限界

係数は**経験則**で決めた。0.9 : 0.45 : 0.35 という比は、

- スパンが1広がるコスト ≒ ポジションが2フレット動くコスト
- 開放弦1本の得 ≒ スパン0.4相当

という感覚に基づく。実際の演奏データから学習したものではない。

**改善の余地**: 「運指の実現可能性と対弦尤度をデータから学習する」研究があり
(arXiv:2204.08094)、この経験則を置き換えられる。`IMPROVEMENTS.md` の B-2 を参照。

### 6.5 満たすべき不変条件

以下は**必ず成り立たなければならない**制約であり、自動テストで検証している。

| 条件 | 理由 |
|---|---|
| `開放弦の音高 + カポ + フレット == 元の音高` | 譜面通りに弾けば元の音が鳴ること |
| 同時発音で同じ弦を使わない | 物理的に不可能 |
| `0 ≤ フレット ≤ max_fret` | 弦上に存在しない位置を指定しない |

## 7. 楽譜の書き出し

### 7.1 MusicXML

分解能は4分音符あたり4(16分音符)。

**音価の丸め込み**: 量子化した長さが表記可能な音価(全/2分/4分/8分/16分と付点)に
一致するとは限らない。表記可能な値のうち、長さを超えない最大のものに丸める。

```
表記可能な音価(tick): 16, 12, 8, 6, 4, 3, 2, 1
                      全  付2 2分 付4 4分 付8 8分 16分
```

**小節をまたぐ音符**: 分割してタイでつなぐのが正式だが、和音との組み合わせで
複雑になるため、**小節線で切る**方式を採用した。実用上、採譜結果の音符は短く、
見た目への影響は小さい。

**休符の充填**: 音符と音符の隙間は、表記可能な音価を大きい方から貪欲に並べて埋める。
これにより**各小節の音価の合計が必ず拍子と一致する**ことを保証する
(これが崩れるとMuseScoreが読み込みに失敗する)。

**TAB譜の表現**: `<staff-details>` に弦の本数とチューニングを書き、
各音符に `<technical><string>/<fret>` を付ける。MuseScoreはこれをTAB譜として解釈する。

### 7.2 MIDI

外部ライブラリを使わず自前で書き出す(依存を増やさないため)。

- フォーマット1。トラック0にテンポと拍子、以降はパートごと
- 可変長数量(VLQ)でデルタタイムを符号化
- ドラムはチャンネル10(0始まりで9)
- 分解能は4分音符あたり480tick

### 7.3 MIDI の読み込み

ADTOF や外部の採譜スクリプトはMIDIで結果を返すため、読み込み側も自前で実装した。

- ランニングステータスに対応
- メタイベント・SysExを読み飛ばす
- **テンポマップを構築**し、ティック→秒の変換をテンポ変化に追随させる
- 閉じられていないノートオンは短い音として拾う

書き出しと読み込みが対になっているため、**往復テスト**で正しさを検証できる。

## 8. エンジン切り替えの設計

### 8.1 登録情報

各エンジンは以下を持つ。

| 項目 | 内容 |
|---|---|
| `id` | 内部的な識別子 |
| `label` | 画面に出す名前 |
| `tier` | `cpu` / `cpu-slow` / `gpu` |
| `desc` | 何が良くなるか・何に注意するか |
| `check` | 利用可能かを返す関数 |
| `hint` | 未導入のときの導入方法 |
| `recommended` | 既定候補かどうか |

### 8.2 利用可否の判定 — find_spec では不十分

当初は `importlib.util.find_spec` で「パッケージが存在するか」を見ていた。
しかし実運用で、**basic-pitchはインストール済みなのに使えない**という状態が発生した。

原因は依存関係のABI不整合だった。

```
basic-pitch → TensorFlow 2.15 → numpy < 2 を要求
            一方 scipy は numpy 2系向けにビルドされていた
            → import 時に ABI エラー
```

`find_spec` はファイルの存在しか見ないため、この状態を「利用可能」と誤判定する。
そこで**実際に import してみる**方式に変更した。TensorFlowの読み込みは数秒かかるため、
結果はプロセス内でキャッシュする。

この経験から、`requirements.txt` で `numpy<2` / `scipy<1.14` を固定し、
セットアップ時に検証と自動修復を行うようにした。

### 8.3 auto の解決順序

```
1. 設定値が具体的なエンジンで、かつ利用可能ならそれを使う
2. auto の場合:
     推奨フラグつき → その他 の順に見て、最初に利用可能なものを使う
     ただし GPU がない環境では tier=gpu のものを飛ばす
3. どれも使えない場合、tier が gpu でないものの先頭を返す
```

3番目の規則は、何もインストールされていない環境で「GPU前提のエンジン」が
既定になってしまう不具合を防ぐためのもの(自動テストで検証している)。
